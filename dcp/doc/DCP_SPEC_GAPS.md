# DCP v1.0 Implementation Gap Inventory

This inventory records the DCP v1.0 differences and ambiguities observed in the current `dcp` module during preparation of the DCP protocol skill. The protocol baseline is the [official DCP v1.0 specification](https://eclipse-dataspace-dcp.github.io/decentralized-claims-protocol/v1.0/); repository observations cite the implementation or existing module documentation. It is a starting point for follow-up work, not a claim that every DCP code path has been audited.

## Implementation gaps

| Priority | Gap | Current evidence | DCP v1.0 requirement |
|---|---|---|---|
| **P0** | Self-Issued ID Token signatures are not verified. | `dcp/dcp-common/src/main/java/it/eng/dcp/common/service/sts/SelfIssuedIdTokenService.java`, `validateToken()`: the `jwt.verify(...)` block is commented out after resolving a JWK. | A Verifier MUST validate the Self-Issued ID Token signature using key material resolved from the `sub` DID document. |
| **P0** | DID key selection and verification relationships are incomplete. | `dcp/dcp-common/src/main/java/it/eng/dcp/common/service/did/HttpDidResolverService.java`, `resolvePublicKey()`, returns the first JWK; `kid` matching and relationship checks are commented out. `DidDocument` and `DidDocumentService` do not emit DID verification relationship properties. | Self-Issued ID Tokens require `capabilityInvocation`; VP proofs require `authentication`; keys must match the referenced verification method and relationship. |
| **P0** | Credential Service access tokens are not reliably used for credential writes. | `IssuerService.authorizeRequest()` validates the incoming token but does not retain its `token` claim. `CredentialDeliveryService.deliverCredentials()` creates a different token with `createAndSignToken(holderDid, null, config)`. | If the Self-Issued ID Token contains a `token` claim, the Issuer MUST use that access token for the requested write to the Holder's Credential Service. |
| **P0** | Status lookups do not bind the request to its original client. | `IssuerController.getRequest()` validates a token and fetches by `requestId`; `IssuerService.getRequestByIssuerPid()` does not compare the token subject with the stored request owner. | The Issuer MUST restrict each request-status resource to the client that created the request. |
| **P1** | Presentation and credential proofs are not validated by the presentation validator. | `PresentationValidationServiceImpl.validate()` checks profile, issuer trust, dates, revocation, and schema, but does not verify VP or VC cryptographic proofs, their verification relationships, or required holder binding. | The Verifier SHOULD perform the specified presentation-validation process; its individual checks include MUST requirements for signatures and relationships, plus holder binding when the dataspace semantics require it. |
| **P1** | `presentationDefinition` can be accepted without being executed. | `DcpController.validatePresentationQuery()` allows a definition-only query. `PresentationService.createPresentation()` selects credentials from `scope`; it does not evaluate a definition or create a `presentationSubmission`. | Presentation Definition support is optional. If unsupported, the Credential Service MUST return `501`; if supported, a response to a definition query MUST include a valid `presentationSubmission`. |
| **P1** | A valid rejected `CredentialMessage` without a reason is rejected by the model. | `dcp/dcp-common/src/main/java/it/eng/dcp/common/model/CredentialMessage.java`, builder validation, requires a non-blank `rejectionReason` when status is `REJECTED`. | `rejectionReason` is optional and may be null. |
| **P1** | Offered credential IDs are not validated as required fields. | `dcp/dcp-common/src/main/java/it/eng/dcp/common/model/CredentialOfferMessage.java`, nested `CredentialObject`: `id` has no required constraint and `build()` does not reject a missing ID. | Each `CredentialObject` MUST have a unique, stable `id`. Its required `type` handling is ambiguous for sparse offers (see below). |
| **P1** | HTTP can be advertised as a DCP service endpoint. | `BaseDidDocumentConfiguration` derives the protocol from `server.ssl.enabled`, which defaults to `false`; `DidDocumentConfig` defaults to `http`. Not every Issuer/Holder client validates the discovered endpoint scheme. | Participants MUST communicate via HTTPS. |

## Security finding

| Priority | Finding | Current evidence | Required action |
|---|---|---|---|
| **P0** | The public DID document included the EC private scalar in its `publicKeyJwk`. | `dcp/dcp-common/src/main/java/it/eng/dcp/common/service/KeyService.java`, `convertPublicKeyToJWK()`, placed the private key parameter `d` alongside public coordinates. `DidDocumentService` publishes this JWK in the DID document's `verificationMethod`. | The published JWK must contain public material only. The code now omits `d`; rotate any signing key whose private parameter may have been exposed, and account for cached or copied DID documents. |

## Multitenancy implementation gaps

These are connector-specific isolation requirements, not DCP v1.0 protocol requirements. DCP defines participant DIDs and protocol messages, but does not define tenant IDs, tenant routing, or tenant data partitions. Keep tenant context internal: do not add `tenantId` to DCP wire messages or repurpose DCP credential scopes as tenant selectors.

| Priority | Gap | Current evidence | Required design/change |
|---|---|---|---|
| **P0** | Holder presentation queries can read credentials across tenants and holders. | `dcp/dcp-holder/src/main/java/it/eng/dcp/holder/service/PresentationService.java` uses `findAll()`, `findByCredentialTypeIn()`, and `findByIdIn()`; `VerifiableCredentialRepository` has no tenant-scoped query methods. `HolderService.createPresentation()` receives the authenticated Holder DID, but the `PresentationService` lookup does not constrain results by it. | Add tenant and authenticated Holder DID constraints to all-credentials, credential-type, and credential-ID lookups. Do not let an ID-scope query bypass either constraint. |
| **P0** | DCP inbound routes do not resolve or bind a tenant context. | `DcpController` uses fixed `/dcp` paths and `IssuerController` uses fixed `/issuer` paths. Unlike the DSP protocol controllers, they do not resolve an enabled tenant or set `TenantContextHolder`. The connector protocol security matchers also do not include tenant-prefixed DCP endpoints. | Add tenant-aware DCP route handling, validate tenant existence/enabled state before processing, and bind the route tenant to the authenticated DCP participant/identity. A path segment alone must not grant cross-tenant access; explicitly configure security for the new paths while preserving DCP token validation. |
| **P0** | Issuer requests and management actions are not tenant-scoped. | `CredentialRequest`, `CredentialRequestRepository`, `IssuerService`, `CredentialDeliveryService`, and `IssuerAPIService` use issuer/request IDs without tenant predicates. Approval, rejection, status lookup, and credential delivery therefore lack a tenant boundary. | Persist tenant ownership and add tenant-constrained reads/writes for request creation, status lookup, approval, rejection, and asynchronous delivery. Bind status access to both the request's tenant and originating client identity. Apply equivalent tenant authorization to DCP management APIs. |
| **P0** | Holder credential and status records have no tenant partition. | `VerifiableCredential` and `CredentialStatusRecord` have no `tenantId`; their repositories query globally or by unscoped IDs. | Add an internal tenant discriminator and scope credential/status persistence and lookups. Include tenant ownership checks on credential delivery and status updates; do not rely on globally unique-looking IDs as authorization. |
| **P1** | Issuer status lists are not tenant-scoped. | `StatusList` is keyed/queried by issuer DID and status purpose, with no tenant discriminator. | Scope list allocation, updates, and retrieval to the tenant's issuer identity. Keep status-list identifiers globally unambiguous where their URLs are public. |
| **P1** | DCP identity and policy configuration are process-wide rather than tenant-selected, and DID document resolution does not support tenant DID paths end to end. | `DcpProperties` and `BaseDidDocumentConfiguration` build one DID, service-entry set, key configuration, and trusted-issuer configuration; metadata configuration is also loaded globally. `GenericDidDocumentController` serves `/.well-known/did.json` from that single configuration. `HttpDidResolverService.fetchDidDocumentCached()` converts a DID to a URL but then reduces it to the base URL and always fetches `/.well-known/did.json`, dropping any DID path. | Select DID, advertised tenant-specific service endpoints, trusted issuers, and issuer metadata/generation policy from validated tenant configuration. Give each tenant a stable DID and key. For `did:web:connector.com:acme_tenant`, serve that tenant's document at the method-standard `https://connector.com/acme_tenant/did.json`; advertise tenant-prefixed service URLs such as `https://connector.com/acme_tenant/dcp`. Do not serve a root `/.well-known/did.json` as a default or active tenant document; an unscoped request must not fall back to any tenant. Update resolution to preserve the DID path and validate the tenant for tenant documents. This path convention follows `did:web` resolution; DCP requires DID-based service discovery but does not prescribe tenant routing or tenant IDs in protocol messages. |
| **P1** | Signing-key metadata and key rotation are global rather than tenant-specific. | `KeyMetadata` and `KeyMetadataRepository.findByActiveTrue()` have no tenant key. `KeyService.rotateAndPersistKeyPair()` creates a self-signed X.509 certificate; `DidDocumentService` publishes only the current key. `KeyRotationAPIController` and `IssuerKeyRotationAPIController` take no tenant selector. | Keep TLS certificates and DCP signing keys separate. DCP v1.0 validates signatures against public keys in the resolved DID document; CA-signing a DCP signing key adds no DCP trust or tenant-isolation benefit. Refactor rotation to select the tenant's signing key and metadata, publish its new public key and `kid`, and retain the old public verification key during token expiry and DID-document cache propagation. Authorize rotation only for that tenant. Do not involve the TLS root/intermediate CA in DCP signing-key rotation. |
| **P1** | Tenant attribution is lost for asynchronous DCP audit events. | `DcpAuditEvent` has no tenant field; `DcpAuditEventListener.handleAuditEvent()` persists on an `@Async` thread, where a request `ThreadLocal` would not be available. | Capture tenant identity in each audit event before dispatch and persist it explicitly; do not depend on inheriting request-thread context. |
| **P2** | In-memory DCP controls are not tenant-aware or shared across connector instances. | `ConsentService` stores records in a process-wide map; `PresentationRateLimiter` keys buckets only by Holder DID; replay protection uses an in-memory `JtiReplayCache`. | Include tenant identity in keys for tenant-sensitive consent/rate limiting. Decide whether replay protection must be shared across replicas; do not treat an in-memory cache as globally effective in a multi-instance deployment. |

Implement tenant resolution and authorization consistently across protocol controllers, management controllers, persistence services, and asynchronous work. Reuse the connector's enabled-tenant validation and request-context lifecycle only through an explicit dependency or DCP adapter; DCP modules do not currently depend on the shared `tools` tenant services. Add cross-tenant integration tests for presentation scope forms, request status and administration, credential delivery, tenant DID/service discovery, disabled or unknown tenants, identity/tenant mismatch, tenant-scoped key rotation, and audit attribution after asynchronous persistence.

### Scope handling risk

`DcpVerifierClient.buildQueryMessage()` copies its `requiredTypes` argument directly into `scope`. `PresentationService.parseScope()` also accepts unqualified strings such as `MembershipCredential` as a compatibility form. DCP defines scopes as `[alias]:[discriminator]` and requires the aliases `org.eclipse.dspace.dcp.vc.type` and `org.eclipse.dspace.dcp.vc.id`. Confirm that interoperable callers supply those forms; a caller-supplied unqualified type string is not one of the two defined standard aliases.

## Existing documentation conflicts

- `dcp/dcp-issuer/API.md` describes `/issuer/requests/{id}/approve` and `/reject` as Issuer Service endpoints, and calls `holderPid` the Holder DID. The approval/rejection API is local administration functionality (the controller is mounted at `/api/issuer`); DCP defines `holderPid` as the Holder-side request ID.
- `dcp/doc/quick_start.md` similarly shows approval/rejection under `/issuer/requests/{id}/...`. These are not DCP v1.0 protocol endpoints.
- The API examples in `dcp/dcp-issuer/API.md` omit required `@context` and `type` properties from the credential request body.

These differences should be handled in implementation/API documentation, not added to the normative DCP skill.

## DCP v1.0 text needing clarification

The following records the schema-led interpretation where the published JSON Schema defines behavior. A schema that conflicts with normative prose is still a specification defect; this inventory uses the schema as the implementation-validation lead as requested, and records prose-only conflicts separately.

1. **Issuer Service discovery — unresolved by schema.** DCP §6.2 literally says the client DID Service MUST publish an `IssuerService` entry in the DID document resolved by the client's DID. The issuance flow also says the Issuer resolves the client's DID to find the Holder's `CredentialService`. There is no Issuer Service discovery message schema that determines whose DID document contains this service entry. Follow the literal §6.2 text only if implementing to the published wording; do not silently substitute the Issuer's DID. Clarification or a specification erratum is needed to make the discovery direction interoperable.
2. **Revocation mechanism — unresolved by schema.** No JSON Schema selects the revocation mechanism. The profile table maps `vc11-sl2021/jwt` to StatusList2021 and `vc20-bssl/jwt` to BitStringStatusList, while §6.10 normatively requires support for “Verifiable Credentials Status List v2021.” The specification's wording/reference does not clearly explain whether §6.10 names the BitStringStatusList specification generically or overrides the profile-specific StatusList2021 choice. Preserve the declared profile mapping and track the §6.10 terminology for protocol clarification; schema validation cannot decide this.
3. **Issuer metadata `credentialsSupported` — schema says required, empty is schema-valid.** The prose calls the property optional, but the published [IssuerMetadata schema](https://eclipse-dataspace-dcp.github.io/decentralized-claims-protocol/v1.0/resources/issuance/issuer-metadata-schema.json) lists it in `required` and defines it as an array without `minItems`. Schema-led behavior: always emit the property; an empty array is valid. The current `CredentialMetadataService` rejects an empty supported-credential configuration, so it should not equate “no supported credential entries” with “omit the required array”; determine whether an empty configuration can be represented as `[]`.
4. **Credential message `type` and `rejectionReason` — schema is defective/inconsistent with prose.** The published [CredentialMessage schema](https://eclipse-dataspace-dcp.github.io/decentralized-claims-protocol/v1.0/resources/issuance/credential-message-schema.json) requires a `type` property but omits `type` from `properties`; under JSON Schema, the required name therefore has no value/type/constant constraint (and additional properties are allowed by default). It separately defines `credentialType` as the constant `CredentialMessage`. Schema-led validation can require `type` to be present, but cannot establish its intended value; the prose and examples say `type` is `CredentialMessage`. The schema types `rejectionReason` as a string, so `null` is not schema-valid even though the prose says it can be null. Emit a string or omit `rejectionReason`; do not send null for schema-valid messages. Track the missing `type` property definition as a schema defect.
5. **Credential offer cardinality — schema allows an empty array, prose does not.** The published [CredentialOfferMessage schema](https://eclipse-dataspace-dcp.github.io/decentralized-claims-protocol/v1.0/resources/issuance/credential-offer-message-schema.json) requires `credentials` but sets no `minItems`; an empty array passes this cardinality rule. Schema-led validators should therefore accept `[]`, despite the prose's “non-empty” requirement, unless the specification is clarified or the schema is corrected.
6. **Sparse credential offers — schema requires `type`, prose permits ID-only entries.** The published [CredentialObject schema](https://eclipse-dataspace-dcp.github.io/decentralized-claims-protocol/v1.0/resources/issuance/credential-object-schema.json) requires both `id` and `type`; it does not allow an ID-only object to validate. Schema-led producers must include both fields, even though the prose describes sparse ID-only entries that the Credential Service expands using metadata. The prose and schema need alignment for cross-implementation interoperability.
7. **Presentation query exclusivity — schema permits both properties, prose rejects both.** The published [PresentationQueryMessage schema](https://eclipse-dataspace-dcp.github.io/decentralized-claims-protocol/v1.0/resources/presentation/presentation-query-message-schema.json) uses `anyOf` with `scope` and `presentationDefinition` each independently satisfying a branch. Therefore, both properties pass the schema (assuming each value is otherwise valid); `scope` is non-empty by `minItems`. The prose requires exactly one and says both must result in HTTP 400. Schema-led validation alone permits both, but this is a case where the prose explicitly imposes an additional protocol behavior; a conformant endpoint should reject both. Correct the schema to `oneOf` or an equivalent mutual-exclusion rule to remove the inconsistency.

For these cases, “schema-led” means validating against the published schema for shapes/cardinality, while still honoring explicit normative protocol behavior that the schema accidentally fails to encode (notably the presentation query's HTTP 400 rule). Do not infer intended values or relax requirements that the schema cannot determine; track schema defects and prose/schema disagreements for upstream clarification.
