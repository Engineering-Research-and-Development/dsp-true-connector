# D-ARC-005 — Loopback calls use an /internal zone and a token signed with an in-memory key

## Context
The connector calls some of its own REST endpoints over HTTP on `localhost`. Five calls do this: offer
validation during a provider-side contract request (`ContractNegotiationProviderService`), the dataset
formats and artifact lookups during a transfer (`AbstractDataTransferService`, `ArtifactTransferService`)
and agreement enforcement (`DataTransferAPIService`, `AgreementService`). They used to target `/api/**`
and authenticate with `CredentialUtils.getAPICredentials()`. In `INTERNAL` mode that minted a
tenant-less `ROLE_ADMIN` JWT with the shared HMAC secret, and the tenant travelled in the
`X-Tenant-Id` header. In `KEYCLOAK` mode it returned the `platform` M2M token, which `/api/**` rejects
since the trusted-issuer registry ([D-ARC-004](D-ARC-004-trusted-issuers-from-config-and-tenant-registry.md))
and must keep rejecting: a `platform` token only reaches protocol endpoints. Without a credential that
works in `KEYCLOAK` mode, provider-side negotiation and transfer fail there.

The constraints: the trust of `/api/**` and of the protocol routes must not widen; the tenant of a
loopback call must not be taken from a header a remote caller could also send; the solution must work in
both authentication modes and with several replicas; no new secret may need provisioning; and the DSP
TCK result must not change.

## Decision
Loopback calls go to a separate `/internal/**` zone with its own security chain (`@Order(0)`), in both
`INTERNAL` and `KEYCLOAK` mode. Each call carries a new token from `InternalCallTokenIssuer` (`tools`):
HMAC-SHA256 with a 256-bit key generated by `SecureRandom` at startup and held in memory only,
`sub=internal-call`, `iss=urn:true-connector:internal`, a 60-second lifetime, the single role
`ROLE_INTERNAL`, and `tenant_id` when the call runs for a tenant. The chain verifies the token only with
that key (signature, `iss`, `exp` with 5 seconds of skew), requires `ROLE_INTERNAL` and a loopback connection
(`127.0.0.1` or `::1`), and sets the tenant context from the verified `tenant_id` claim; `X-Tenant-Id` is
never read there. Only the five loopback callers use the zone. `DISABLED` mode permits all requests, as on
the other chains. Both the TCP peer (`getRemoteAddr()`) and the local socket address (`getLocalAddr()`)
must be loopback, so the check holds even when a forward-headers strategy (auto-enabled on Kubernetes)
rewrites the remote address from `X-Forwarded-For`: the local address is never rewritten, and a connection
to `127.0.0.1` or `::1` only arrives over the loopback interface. `internal` is reserved as a tenant ID,
because the chain's `/internal/**` matcher would otherwise catch that tenant's protocol paths. The former `internal-service` token path (`getAPICredentials()`,
`InternalServiceTokenIssuer`, `InternalServiceAuthenticationProvider`) is removed, and the two routes used
only by loopback calls (`offers/validate`, `agreements/{id}/enforce`) move from `/api` to `/internal`.

## Alternatives Considered
- **Leave the loopback calls broken in `KEYCLOAK` mode until the admin-realm work (K6)** → rejected
  because provider-side negotiation and transfer would fail in `KEYCLOAK` mode for the whole slice, and
  the slice's end-to-end QA could only prove catalog requests.
- **A Keycloak super-admin client in `connector-admin` for loopback calls** → rejected because it gives
  a long-lived, network-usable credential with super-admin rights to every replica, needs a secret to
  provision and rotate, couples the loopback path to Keycloak availability, and does nothing for
  `INTERNAL` mode.
- **In-process service calls instead of HTTP** → not chosen now because the callers live in other
  modules (`negotiation`, `data-transfer`) than the services they call (`catalog`, `negotiation`), and
  replacing the HTTP hop means new cross-module service contracts. It stays a possible later refactor that
  would make this zone unnecessary.
- **A shared secret configured for internal calls** → rejected because it is one more secret to
  provision, rotate and keep out of logs, and anyone who obtains it can mint internal tokens for any
  replica. A key that never leaves the process removes that class of leak.

## Rationale
A key generated per process means a token can only be verified by the process that minted it; nothing
outside the JVM can forge one, and there is nothing to configure, rotate or leak through configuration.
Every loopback call targets `localhost`, so the verifying process is always the signing one, which keeps
the design correct with several replicas. The separate zone keeps `/api/**` and the protocol routes
untouched: their decoders do not know the key, so an internal token gets 401 there, and a Keycloak or
`INTERNAL`-mode user token gets 401 on `/internal/**`. Putting the tenant in the signed token instead of a
header closes the path where a tenant-less principal could pick a tenant with `X-Tenant-Id`. A 60-second
token minted per call needs no cache and no retry-on-401. The loopback check bounds the damage of a token
that leaks (for example, from a log) to callers already on the host. The same mechanism in both modes means
one code path for the callers and one chain to test, covered by `InternalCallTokenIssuerTest`,
`InternalCallSecurityIT`, `KeycloakInternalCallSecurityIT`, `MultitenantInternalAPIIT` and
`DisabledSecurityIT`.

## Consequences

### Positive
- Provider-side negotiation and transfer work in `KEYCLOAK` mode without widening trust on `/api/**`.
- No new secret, property or Keycloak client.
- The tenant of a loopback call is fixed by the caller's tenant context and cannot be changed by a header.
- `/internal/**` is absent from the published OpenAPI documentation (`@Hidden`), so it is not a public API.

### Negative
- `POST /api/v1/offers/validate` and `POST /api/v1/agreements/{id}/enforce` are removed (404). External
  clients that called them must stop; the UI did not use them.
- Two dataset lookups exist twice, under `/api/v1/datasets` for the UI and under `/internal/v1/datasets`
  for loopback calls.
- Loopback calls still pay an HTTP round trip and a token signature per call.
- A tenant cannot use the ID `internal`.

### Risks
- A forwarding configuration (`server.forward-headers-strategy`, or Spring Boot's automatic one on
  Kubernetes) lets a remote caller appear as `127.0.0.1`. Mitigation: the local socket address must also be
  loopback, and the token is still required and cannot be forged without the in-memory key.
- A future caller targets another host or replica instead of `localhost`, and its token fails
  verification there. Mitigation: `OkHttpRestClient.sendInternalRequest` and `sendInternalPostRequest`
  always build a `localhost` URL; a non-local target fails closed
  with 401.
- An internal token leaks into a log. Mitigation: the issuer never logs tokens or the key, tokens expire
  after 60 seconds, and they are accepted only from loopback.
